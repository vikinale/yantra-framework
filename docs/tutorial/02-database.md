# 2. Database & Models

In this step you'll create the `posts` table with a migration, add a `Post` model, seed some starter rows, and run both from the CLI. By the end the blog has real data to work with.

::: tip You'll need step 1 first
This step assumes you've completed [1. Setup & First Route](/tutorial/01-setup) — a scaffolded app with a working `.env` and database connection. Run `php vendor/bin/yantra db:check` to confirm the connection before continuing.
:::

## Create the migration

Migrations are version control for your schema. Generate one:

```bash
php vendor/bin/yantra make:migration create_posts_table
```

This writes a timestamped file to `database/migrations/`, e.g. `2026_07_06_120000_create_posts_table.php`. Open it and replace the body with the following. Note the type hints: `up()` and `down()` receive a `System\Database\Database` — **not** a raw `PDO`.

```php
<?php
declare(strict_types=1);

use System\Contracts\MigrationInterface;
use System\Database\Database;
use System\Database\Schema\Schema;
use System\Database\Schema\Blueprint;

return new class implements MigrationInterface {
    public function up(Database $db): void
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->increments('id');
            $table->string('title', 200);
            $table->string('slug', 200)->unique();
            $table->text('body');
            $table->boolean('published')->default(true);
            $table->timestamps();
        });
    }

    public function down(Database $db): void
    {
        Schema::dropIfExists('posts');
    }
};
```

A few things to know about `Blueprint`:

- `increments('id')` gives you an auto-increment primary key (`INT UNSIGNED AUTO_INCREMENT PRIMARY KEY` on MySQL).
- Modifiers like `->unique()`, `->default()`, and `->nullable()` always apply to the **last column added** — order your chains accordingly.
- `timestamps()` adds nullable `created_at` and `updated_at` `DATETIME` columns.

The full column and modifier reference is in [Migrations](/database/migrations).

::: warning Gotchas
- The migration file must **`return`** the migration instance. A bare class definition (no `return new ...`) fails with "Invalid migration file (must return MigrationInterface)".
- The stub generated by `make:migration` may type-hint `PDO`. Change those hints to `Database` (as above) or the class won't satisfy `MigrationInterface`.
:::

## Run the migration

```bash
php vendor/bin/yantra migrate
```

You should see the `create_posts_table` migration applied. Useful companions:

```bash
php vendor/bin/yantra migrate:status      # show ran / pending
php vendor/bin/yantra migrate:rollback    # undo the last batch
```

## Create the `Post` model

Models are a thin convenience layer over the query builder. Create `App/Models/Post.php`:

```php
<?php
declare(strict_types=1);

namespace App\Models;

use System\Database\Model;

class Post extends Model
{
    protected ?string $tableName = 'posts';

    /** Mass-assignable columns */
    protected array $fillable = [
        'title',
        'slug',
        'body',
        'published',
    ];

    protected array $casts = [
        'published' => 'bool',
    ];
}
```

`$tableName` binds the model to the table, `$fillable` whitelists mass-assignable columns (so `create()` and `fill()` ignore anything else), and `$casts` coerces attribute types when you read them.

### Reading and writing — know your return types

This is the single most important thing to get right with Yantra models. Some methods return **raw arrays**, others return **model instances**:

| Call | Returns |
|---|---|
| `Post::all()` | `array` of raw rows |
| `(new Post)->get()` / `->first()` | raw array / raw row (or `null`) |
| `(new Post)->find($id)` | raw row array (or `null`) |
| `(new Post)->getModels()` | array of `Post` instances |
| `(new Post)->firstModel()` | one `Post` instance (or `null`) |
| `(new Post)->findModel($id)` | one `Post` instance (or `null`) |
| `(new Post)->create([...])` | the new row's **id** (`int`\|`string`) |

```php
use App\Models\Post;

// Raw arrays — access with $row['title']
$rows = Post::all();
$row  = (new Post)->find(1);

// Model instances — access with $post->title (casts + accessors apply)
$posts = Post::query()->orderBy('created_at', 'DESC')->getModels();
$post  = (new Post)->findModel(1);

// Insert; create() returns the new id
$id = (new Post)->create([
    'title' => 'Hello Yantra',
    'slug'  => 'hello-yantra',
    'body'  => 'My first post.',
]);
```

::: warning Gotchas
- There is **no `findOrFail()`**. `find()`/`findModel()` return `null` when nothing matches — check for it yourself (e.g. `?? abort(404)`).
- `find()`, `first()`, `get()`, and `all()` return **raw arrays**. Use the `...Model` variants (`findModel`, `firstModel`, `getModels`) when you want objects you can access as `$post->title`.
- The query builder has `count()` and `exists()` but **no** `sum`/`avg`/`max`/`min`, `having()`, or `increment()`. Reach for `selectRaw()` if you need an aggregate.
:::

## Write a seeder

Seeders populate the database with starter or test data. Generate one:

```bash
php vendor/bin/yantra make:seeder PostsTableSeeder
```

Edit `database/seeders/PostsTableSeeder.php`. Implement `SeederInterface` and use the injected `Database` — but you're free to use the model inside `run()`:

```php
<?php
declare(strict_types=1);

namespace Database\Seeders;

use System\Contracts\SeederInterface;
use System\Database\Database;
use App\Models\Post;

final class PostsTableSeeder implements SeederInterface
{
    public function run(Database $db): void
    {
        $posts = [
            ['Welcome to the blog', 'welcome-to-the-blog', 'This is the very first post.'],
            ['Why zero dependencies', 'why-zero-dependencies', 'Yantra ships with no runtime deps.'],
            ['Building CRUD',         'building-crud',         'Next we wire up create, read, update, delete.'],
        ];

        foreach ($posts as [$title, $slug, $body]) {
            (new Post)->create([
                'title'     => $title,
                'slug'      => $slug,
                'body'      => $body,
                'published' => true,
            ]);
        }
    }
}
```

### Compose from the root seeder

There is **no `call()` method**. The default `DatabaseSeeder` delegates by instantiating other seeders and invoking their `run()` directly. Edit `database/seeders/DatabaseSeeder.php`:

```php
<?php
declare(strict_types=1);

namespace Database\Seeders;

use System\Contracts\SeederInterface;
use System\Database\Database;

final class DatabaseSeeder implements SeederInterface
{
    public function run(Database $db): void
    {
        (new PostsTableSeeder())->run($db);
    }
}
```

## Run the seeder

```bash
# Runs Database\Seeders\DatabaseSeeder
php vendor/bin/yantra db:seed

# Or run just one class
php vendor/bin/yantra db:seed --class=Database\\Seeders\\PostsTableSeeder
```

Confirm the rows exist:

```bash
php vendor/bin/yantra db:check
```

::: warning Gotchas
- The `make:seeder` stub may type-hint `PDO`; the runner passes a `System\Database\Database` per `SeederInterface`. Update the hint to `Database` as shown.
- Seeders aren't wrapped in a transaction and aren't idempotent — re-running this seeder a second time hits the `slug` unique constraint. Wipe the table (or use `migrate:refresh --force`) before re-seeding.
:::
